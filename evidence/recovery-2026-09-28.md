# Recovery and failure-boundary evidence, 2026-09-28

This covers Phase 11 of the playbook: realistic failure boundaries across
`slasettle-vault`'s contracts and `slasettle-hub`'s watcher, indexer, SDK,
and frontend. It does not attempt every theoretical failure; it prioritizes
money movement, transaction correctness, watcher behavior, indexer
correctness, state consistency, duplicate execution, network interaction,
and recovery after partial completion, per the playbook's own priority
list.

## Read-only recovery audit, mapped to actual implementation

| Concern | Component | Existing mechanism |
|---|---|---|
| RPC failure retry | indexer | `withNetworkRetry` in `src/rpc/client.ts`: 3 attempts, linear backoff, distinguishes a transient network error (no `.response` on the AxiosError) from a real HTTP error response, which is never retried |
| RPC failure retry | watcher | mocked-RPC tests in `internal/contract/contract_rpc_test.go` cover transport failure at both the simulation and submission stages; no retry loop exists in the daemon itself, a failed round is logged and simply retried next round (see watcher/README.md's documented limitation) |
| Transaction confirmation | watcher | `submitAndPoll` polls `GetTransaction` until a terminal status; tests cover poll timeout and transient not-found-then-success |
| Transaction confirmation | frontend | `lib/use-transaction.ts` drives build to sign to submit to poll, exposing distinct `building`/`signing`/`submitting`/`confirmed`/`failed` states; nothing is shown as confirmed before `pollTransaction` returns a definitive status |
| Indexer ingestion / duplicate processing | indexer | checkpoint and event batch written in a single SQLite transaction (`db.ts`'s `applyBatch`); `checks` table uses `INSERT OR IGNORE` keyed on the event's own id |
| Database writes | indexer | `better-sqlite3`'s synchronous transaction wrapper; either the whole batch (checkpoint + rows) commits or none of it does |
| Process restart | indexer | resumes from the stored RPC cursor, not `START_LEDGER`, once a checkpoint exists |
| Watcher restart | watcher | `has_watcher_voted` is checked live before submitting, specifically to avoid a wasted/duplicate submission after a restart |
| Stale state | indexer | none of the indexed tables carry a TTL or generation number; a stale row is only ever corrected by a later real event, never a client-side inference |
| Malformed data | indexer | `classifyEvents` logs and skips an unrecognized topic rather than throwing; `decode.ts` never coerces amounts to `Number` |

## Finding A: zero-balance withdrawal

**Result of investigation:** this was a genuine correctness/consistency
problem, not a fund-safety bug (the transfer was already correctly guarded
by `balance > 0`, so no funds were ever at risk). It has been **fixed**.

- Before the fix: a repeat `withdraw_remaining_bond` call on an
  already-exhausted balance succeeded as a silent no-op, transferring
  nothing but still charging a real transaction fee and emitting a
  `BondWithdrawn` event with `amount: 0`, which is inconsistent with this
  contract's existing pattern of rejecting other degenerate zero-value
  calls (`create_sla`'s zero bond/penalty checks, `top_up_bond`'s zero
  amount check).
- Fix: rejects with `Error::InvalidAmount` when the balance is already
  zero, before attempting any transfer.
- Regression test: `test_withdraw_remaining_bond_twice_fails_second_time`
  in `contracts/sla_vault/src/test.rs`, reproducing cancel, withdraw once,
  withdraw again.
- Status: **TESTED LOCALLY** (`cargo test -p sla-vault`, targeted and full
  workspace, 46/46 passing). Not re-verified live against the fresh
  Testnet deployment in this pass; the fixed contract has not been
  redeployed since this change. That redeployment and live re-verification
  is a real next step, not done here.

## Finding B: indexer registration/removal ordering

**Result of investigation:** this was a genuine correctness bug, confirmed
by tracing the actual code path, and by directly reproducing it against
the real historical data from Phase 10. It has been **fixed**.

- Root cause: `applyBatch` ran every watcher registration in one loop, then
  every removal in a separate loop, discarding the real chronological
  order when both appeared in the same ingestion batch.
- Reproduction chain, as required by the playbook:
  - on-chain order: watcher5 register (ledger 4905614) then remove (ledger
    4905637) then re-register (ledger 4905642), all landing in one
    ingestion cycle
  - event extraction order: `getEvents` returns events in ledger order,
    unchanged
  - event classification order (before the fix): `classifyEvents` put the
    two registrations into one array and the one removal into a second
    array, losing the interleaving
  - database application order (before the fix): `applyBatch` ran both
    registrations, then the removal, so the removal (chronologically the
    middle event) landed last and won
  - final watcher state (before the fix): `removed_at` set, so
    `GET /v1/watchers` incorrectly excluded watcher5
- Fix: a single `watcherEvents` array, ordered by real event order, applied
  in one loop with the same two prepared statements, dispatched per event
  type instead of grouped by type.
- Regression tests: `classify.test.ts` confirms `classifyEvents` preserves
  interleaved order; `db.test.ts` adds a test reproducing the exact
  register-remove-re-register-in-one-batch shape and asserts the final
  state is correctly not-removed.
- **VERIFIED LIVE**: the fixed indexer was pointed at a clean database and
  the real Phase 10 ledger range (`START_LEDGER=4905580`) was re-ingested.
  `eventsProcessed: 22` matched exactly, and `GET /v1/watchers` now
  correctly lists all 5 watchers, including watcher5, which the pre-fix
  code had excluded. This is the actual real event stream that exposed the
  bug, reprocessed with the fix in place, not a synthetic reproduction.

  comments): a transient `fetch failed` against the RPC host was retried

## Duplicate execution

- Duplicate watcher vote: **VERIFIED LIVE** in Phase 10 (a real rejected
  transaction, `Error(Contract, #4)` = `DuplicateCheck`).
- Duplicate settlement: **VERIFIED LIVE** in Phase 10 (a real rejected
  transaction, `Error(Contract, #4)` = `AlreadySettled`).
- Duplicate indexer event / repeated ingestion after restart: **VERIFIED
  LIVE** in this pass (see Process restart below): the same 22-event
  ledger range was ingested twice (once as a clean-database reprocess for
  the Finding B fix, once implicitly as part of every `runOnce` call
  re-checking the checkpoint) with no duplicate rows, confirmed by row
  counts before and after.
- Both protections are distinct: the contract-level ones (vote, settlement)
  are enforced on-chain and are the actual source of truth; the
  indexer-level one (`INSERT OR IGNORE` on event id) is a separate,
  necessary idempotency layer for the indexer's own database, since the
  indexer can legitimately re-observe the same on-chain event range after
  a restart.

## Database interruption

Reasoned through rather than physically interrupted, since deliberately
killing the process mid-write against the real database is destructive to
test safely: `applyBatch` wraps the checkpoint write and every row insert
in one `better-sqlite3` synchronous transaction. `better-sqlite3` transactions
are ACID via SQLite's own journal; either the whole transaction commits
(checkpoint advances and rows land together) or the whole thing rolls back
(checkpoint stays at its previous value and no partial rows are written),
so a crash mid-write cannot produce a checkpoint that is ahead of what was
actually stored. On restart, the unchanged checkpoint causes the same
ledger range to be re-fetched and reprocessed, which `INSERT OR IGNORE`
handles idempotently. **LOGICALLY COVERED**, not live-tested by an actual
kill-mid-write in this pass.

## Wrong network

- Contract IDs are configured per-deployment via environment variables in
  both the indexer and the frontend, never hardcoded; there is no code
  path that could silently point at an unintended contract ID.
- The frontend has a real, working detection mechanism: `NetworkIndicator`
  compares the connected Freighter wallet's actual `networkPassphrase`
  against the app's configured `NEXT_PUBLIC_NETWORK_PASSPHRASE` and shows
  a visible "Wallet network mismatch" warning when they differ. Read
  directly from `components/network/network-indicator.tsx`.
- **Real gap found**: this mismatch is only ever shown as a warning badge.
  Nothing in `use-transaction.ts` or the write-action forms checks it
  before allowing a submit. In practice this is not a silent-wrong-network
  execution risk, because Stellar's transaction signing includes the
  network passphrase in the signed payload itself; a transaction signed
  for one network and submitted to RPC configured for another fails at the
  network/signature level rather than silently executing against the wrong
  contract. This is **LOGICALLY COVERED** by Stellar's own protocol design,
  not live-tested here (doing so would require connecting a real wallet on
  a mismatched network, which needs browser/Freighter access not available
  in this environment). The UX gap (no hard client-side block, only a
  warning) is real and recorded as a **KNOWN LIMITATION**, not fixed in
  this pass.
